# Посадочные страницы и товарный фид магазина отделочных материалов

Две продающие страницы под контекстную рекламу — плитка с керамогранитом и напольные
покрытия — с квизом-калькулятором, приёмом заявок и выгрузкой товарного фида для
Яндекс.Директа. Статика, никакой CMS: контент приезжает из выгрузки каталога магазина.

## Состав

| Каталог | Что это |
|---|---|
| `site/` | Astro 7, статическая сборка. Отдаётся nginx, он же проксирует `/api/` |
| `api/` | Приём заявок: Bun + SQLite, без единой зависимости. Локальная разработка и стенд |
| `api-php/` | Тот же приём заявок на PHP 8 + MySQL — версия для боевого хостинга |
| `deploy/` | `.htaccess` боевого сайта: маршруты, кэш, заголовки |
| `pipeline/` | Python: выгрузка каталога (CSV) → `catalog.json` → YML-фиды и данные для витрины |
| `docker-compose.yml` | Локальный запуск |
| `docker-compose.prod.yml` | Стенд на сервере: те же образы, лимиты памяти, порт наружу |

Внутренние рабочие документы проекта и материалы заказчика в репозиторий не входят —
см. `.gitignore`, там расписано, что и почему остаётся на рабочей машине.

## Локальный запуск

На хосте нужен только Docker:

```bash
docker compose up -d --build
# сайт      → http://localhost:8104/poly
# заявки    → http://localhost:8105/health
```

Порты 8104/8105 выбраны как свободные, менять — сверившись с `docker ps`.

## Пайплайн каталога

Работает на стандартной библиотеке Python 3.13, ставить нечего:

```bash
python3 pipeline/build_catalog.py    # выгрузка CSV → data/catalog.json
python3 pipeline/build_feed.py       # → data/feeds/*.yml для Яндекс.Директа
python3 pipeline/build_showcase.py   # → витрина и данные квиза в site/
python3 pipeline/fetch_images.py     # фото товаров → WebP в site/public/showcase/
```

Сама выгрузка каталога в git не ходит: в ней есть закупочные цены магазина.
Подробности — `pipeline/README.md`.

## Два приёмника заявок, одна логика

Боевой сайт живёт на виртуальном хостинге: там нет root, а значит нет ни Docker,
ни Bun — только PHP и MySQL. Поэтому у приёма заявок две реализации с одинаковым
поведением: `api/server.ts` (Bun + SQLite) для локальной разработки и стенда,
`api-php/index.php` (PHP 8 + MySQL) для боевого хостинга.

Совпадают: правила валидации, honeypot и порог времени заполнения, антифлуд
5 заявок с адреса за 10 минут, набор полей, коды и тексты ответов, одноразовые
ссылки на PDF лид-магнитов. Фронтенд не знает, какая версия за `/api/`.

Правя одну, править обе — иначе стенд и бой начнут расходиться в поведении.

Пароли от базы, токен бота и адрес получателя заявок лежат в конфиге **на сервере,
вне корня сайта и вне репозитория** — шаблон в `api-php/config.example.php`.
Схема таблиц — `api-php/schema.sql`.

## Выкатка

Push в `master` → GitHub Actions собирает статику на раннере и заливает по SFTP
готовый результат: `dist` + `.htaccess` + один PHP-файл API. Затем проверяет, что
страница отдаётся, API отвечает, а несуществующий адрес возвращает 404.

Хост, пользователь, путь и ключ заданы секретами репозитория
(`HOSTING_HOST`, `HOSTING_USER`, `HOSTING_PATH`, `HOSTING_SSH_KEY`), адрес сайта
и разрешение на индексацию — переменными (`PUBLIC_SITE_URL`, `PUBLIC_INDEXABLE`).

Выкатка стенда на VPS (`deploy.yml`, Docker) осталась ручной — кнопкой Run workflow.

**Грабля:** `PUBLIC_SITE_URL` и `PUBLIC_INDEXABLE` печатаются в статику на этапе сборки
(canonical, OG, `robots.txt`). Меняются только пересборкой — залить файлы поверх мало.
Пока сайт закрыт от индексации: `PUBLIC_INDEXABLE=0`.

**Грабля:** домен кириллический. В адресах, сертификатах и конфигах он живёт
в punycode — на глаз это разные строки, а совпадать они должны точно.
